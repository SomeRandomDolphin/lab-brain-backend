# Pinned explicitly (whisperx itself declares omegaconf>=2.3.0, but only as a
# transitive dependency — it never appears as its own line here). During pip's
# resolver backtracking (triggered by transformers/openai having many
# candidate versions to negotiate against), omegaconf silently fell out of
# the final resolved set entirely — no install-time error, just a missing
# package. At runtime this surfaced as `ModuleNotFoundError("No module named
# 'omegaconf'")` deep inside whisperx.load_model()'s VAD setup, which
# asr.py's broad `except ImportError` caught and misreported as "whisperx
# unavailable", silently degrading to the faster-whisper fallback. Same root
# cause class as the torchaudio/torchvision pins above — an unpinned
# transitive dependency at the mercy of resolver backtracking — just a
# missing-module symptom instead of an ABI mismatch. Pin whatever else
# whisperx pulls in transitively the same way if this recurs for a different
# module.

# Pinned exact (not >=): torch>=2.1.0 previously resolved to 2.8.0, whose
# weights_only=True default breaks pyannote VAD checkpoint loading (see
# app/pipeline/asr.py's add_safe_globals fix). Pinning avoids a future
# rebuild silently resolving to yet another breaking torch release.
torch==2.8.0
# Pinned exact and listed explicitly (not left to whisperx's torchaudio~=2.8.0
# / torchvision~=0.23.0 and pyannote.audio's torchaudio>=2.8.0 transitive
# constraints): with only torch pinned, pip's resolver has to backtrack across
# the whole dependency graph (transformers, openai, etc. all have many
# candidate versions), and during that backtracking it can land on a
# torchaudio build whose compiled ABI doesn't match whatever torch build it
# settled on for that run — a bare version pin like `torchaudio==2.8.0`
# doesn't prevent this, since PEP 440 `==` matching doesn't reliably
# discriminate on the +cpu local-version segment that distinguishes the CPU
# build from the default CUDA-ABI build on PyPI. Mismatched ABI fails at
# import time with `OSError: ... undefined symbol: torch_library_impl`
# rather than at install time, so it isn't caught by a successful `pip
# install`. See the Dockerfile's builder-stage RUN step, which appends
# `+cpu` to exactly these three pins (in one atomic install, not a separate
# step — see that step's own comment for why sequential installs reintroduce
# this same problem) when building for CPU-only inference.
torchaudio==2.8.0
torchvision==0.23.0
transformers>=5.14.1
